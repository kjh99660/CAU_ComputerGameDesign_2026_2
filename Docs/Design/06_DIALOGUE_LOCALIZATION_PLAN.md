# 대사 한·영 지원(i18n) 계획

> 상태: `TextManager`와 시작 화면의 언어 버튼을 구현했다. 아래 1절부터는 구현 전 비교·설계 기록이다.
>
> 기준 확인일: 2026년 11월 24일, 커밋 `0093036`(`ui/screen-effects`) 기준
>
> 구현 범위: 도입·마무리(성과별 분기 포함), 전투 무전, 스폰 경고와 화자 이름. 다른 UI 라벨은 그대로 영문이다.

## 현재 사용법

- 시작 화면 오른쪽 위 `EXIT` 아래의 `LANG: KOR` / `LANG: ENG`를 누른다. 처음에는 한국어이고, 선택은 `PlayerPrefs`(`REBOOT.DialogueLanguage`)에 저장한다.
- Unity에서 `Main` 또는 `Main_NeonCity`를 열고 `Manager > TextManager`를 선택한다. Inspector의 **Korean dialogue**와 **English dialogue**에서 내용을 편집한 뒤 해당 **Save TXT**를 누른다. 다음 Play 시작 때 반영된다.
- 실제 문구는 `Assets/Resources/DialogueKorean.txt`와 `DialogueEnglish.txt`의 UTF-8 JSON에 있다. 기존 `DialogueSequence.asset`에서 줄 순서, 화자 방향, 무전 시각, 분기 조건을 가져오므로 문구를 수정할 때 배열의 줄 수와 순서를 유지한다. 파일이 잘못되면 경고를 남기고 원래 시퀀스를 사용한다.

## 구현 전 계획 (참고)

다국어 지원(i18n) 기능은 지금 없다. 다만 화면의 UI 글자는 이미 전부 영어라서, 영어판에 필요한 것은 대사와 화자 이름(`노아`)뿐이다.

**권장.** 대사 줄마다 영어 칸을 더하고, 에셋의 기본 언어 값으로 한국어판과 영어판을 고른다(2절의 나, 필수 단계, 추정 6.5시간). Start 화면에서 게임을 켠 채로 언어를 고르는 버튼은 그다음의 선택 단계로 둔다(추가 9시간 이상). 버튼은 빌드 하나로 두 언어를 번갈아 보여 줘야 할 때만 필요하다. 팀이 먼저 정할 것은 영어판이 어디에 필요한지다(9절 1번).

결정만 하려면 2절과 9절을 읽으면 된다. 3~5절은 구현하는 사람을 위한 내용이다. 대사 문장 자체는 `05_STORY_AND_SCRIPT.md`가 원본이다.

## 1. 지금 상태

- 다국어 지원은 없다. Unity Localization 패키지, 언어 설정 코드, 언어 저장(`PlayerPrefs`)이 모두 없다.
- UI 라벨은 영어다. 프리팹의 고정 라벨 24개와 코드가 넣는 `READY`, `START`가 전부 영문이다.
- 한국어인 것은 세 가지다.
  - 대사 10줄(`Assets/Resources/DialogueSequence.asset`, 도입 6줄과 마무리 4줄)
  - 화자 이름 `노아` (`K-7`은 두 언어에서 같다)
  - 대사 묶음이 비었을 때만 보이는 임시 문구 3개(`DialoguePresenter.cs` 89~90행)
- 대화 글꼴(IBM Plex Sans KR, 실행 중 만드는 동적 폰트)에는 영문 95자와 한글 11,172자가 모두 있다. 영어 대사를 위해 글꼴을 바꿀 필요가 없다.
- 대화 글꼴에 없는 글자가 있다. é 같은 악센트 문자는 TMP 설정상 기본 글꼴(LiberationSans)로 바뀌어 그려져 서체가 섞인다. 줄바꿈 없는 공백은 보통 공백으로 대신 그려진다. 둘 다 화면에서 확인한 것은 아니고 설정과 패키지 소스를 읽은 결과다.
- UI 글꼴(Chakra Petch 정적 에셋)에는 한글이 없다. 그래서 언어 선택 버튼을 만든다면 글자는 영문으로 적는다.
- `05` 문서의 대사는 한국어와 영어 모두 실제 대화 상자에서 한 행에 들어간다(10절의 측정).

## 2. 고를 수 있는 방법

| 방법 | 내용 | 추정 | 한계 |
| --- | --- | --- | --- |
| 가. 영어 에셋 교체 | 영어 대사 에셋을 하나 더 만든다. 영어로 보여 줄 때만 씬의 `UIRoot`에 있는 `dialogueData` 칸에 그 에셋을 넣고 실행한다 | 약 2.5시간. 코드 변경 없음 | 게임을 켠 채로는 언어를 바꿀 수 없다. 에셋을 넣은 씬을 커밋하면 기존 PlayMode 대화 테스트가 실패하므로(한국어 에셋의 글자와 화면을 비교한다) 커밋하지 않고 그때마다 손으로 넣는다. 빌드로 보여 주려면 그 상태로 따로 빌드한다. 한국어 줄을 고치면 영어 에셋도 따로 고쳐야 한다 |
| 나. 줄마다 영어 칸(권장) | 대사 줄마다 영어 칸을 더하고 에셋의 기본 언어 값으로 언어를 정한다. 선택 단계로 Start 화면에 `KOR / ENG` 버튼을 더한다 | 필수 단계 6.5시간. 버튼까지 넣으면 15시간 이상 | 구현 전이라 시간은 추정이다. 버튼이 없으면 플레이어가 게임 안에서 언어를 고를 수 없다(3절의 '영어판을 띄우는 방법') |
| 다. 한·영 동시 표기 | 한 줄에 한국어와 영어를 줄바꿈으로 함께 넣는다. 대사 상자가 2행이라 위에 한국어, 아래에 영어가 나온다 | 약 2시간. 코드 변경 없음 | 언제나 두 언어가 함께 나온다. 타이핑이 한국어 다음에 영어 순서라 도입 전체가 약 11초 걸린다(지금은 약 4초). 화자 칸에는 `노아 / Noa`처럼 함께 적는다. 나와 함께 쓸 수 없다(5절의 줄바꿈 금지) |

- 가와 다의 시간은 에셋 입력, 테스트 한 개, 수동 확인을 합친 추정이다.
- 나를 권하는 이유는 세 가지다. 에셋이 하나라서 두 언어의 줄 수가 어긋날 수 없다. 번역 누락과 줄 넘침을 테스트로 막을 수 있다. 대사 변형(`05` 4.4)이 들어와도 조건값을 두 에셋에 중복해 두지 않는다.
- 다는 실제 대화 상자에서 확인했다. `05` 문서의 모든 줄이 한국어 한 행, 영어 한 행으로 들어가고 잘리지 않았다. 타이핑 연출이 어떻게 보이는지는 눈으로 보지 않았다.

어느 것을 고를지는 영어판이 어디에 필요한지에 달렸다.

| 영어판이 필요한 자리 | 맞는 방법 |
| --- | --- |
| 영어로 한 번 보여 주면 된다(영상, 영어 실행 한 번) | 가, 또는 나의 필수 단계 |
| 빌드 하나로 발표 중에 두 언어를 번갈아 보여 준다 | 나의 필수 단계와 버튼 |
| 한국어를 쓰는 사람과 영어를 쓰는 사람이 함께 본다 | 다 |

## 3. 권장안의 구조

### 데이터

에셋은 지금처럼 하나(`Resources/DialogueSequence.asset`)다. 줄마다 영어 본문 칸을 더한다.

```csharp
public enum DialogueLanguage { Korean = 0, English = 1 }

[Serializable]
public struct DialogueLine
{
    public string speaker;                    // 화자 키이자 한국어 이름(그대로)
    [TextArea(2, 5)] public string text;      // 한국어 본문(이름과 직렬화 그대로)
    [TextArea(2, 5)] public string textEn;    // 영어 본문(신규)
    public bool leftSpeaker;
}

[Serializable]
public struct DialogueSpeakerName { public string speaker; public string nameEn; }
```

`DialogueSequenceData`에 더하는 필드는 둘이다. 값은 모두 임시값이다.

| 필드 | 기본값 | 뜻 |
| --- | --- | --- |
| `speakerNames` | 노아 → `Noa`, K-7 → `K-7` | 화자의 영어 이름 표. 줄마다 적지 않아 같은 인물이 다르게 번역될 수 없다 |
| `defaultLanguage` | `Korean` | 대화에 쓸 언어 |

- `text`의 이름을 바꾸지 않는다. 기존 YAML이 그대로 읽히고, `data.intro[i].text`를 읽는 기존 테스트가 같은 뜻으로 컴파일된다.
- 새 칸이 빈 줄은 `null`일 수도 빈 문자열일 수도 있다. 판정은 `string.IsNullOrEmpty`로 한다.
- 영어 타이핑 속도 배율(영어는 글자 수가 한국어의 약 2배다)은 필수가 아니다. 넣는다면 필드 하나와 `DialoguePresenter.cs` 45행의 곱셈 하나다.

### 실행 흐름(필수 단계)

1. 대화 상태(IntroDialogue, OutroDialogue)에 들어올 때 `DialoguePresenter`가 에셋의 `defaultLanguage`를 읽는다. 그 대화 동안은 그 언어다.
2. 순수 함수 `DialogueLocalizer.Resolve`가 화면에 나갈 문자열만 담은 새 배열을 만들어 기존 `DialogueProgress.Begin`에 넘긴다. 고치는 곳은 `DialoguePresenter.cs` 32행 한 줄이다.
3. 한국어일 때 `Resolve`는 `speaker`, `text`, `leftSpeaker`를 그대로 복사한다. 공백 다듬기나 치환을 하지 않는다. 그래야 화면 글자를 에셋과 비교하는 기존 테스트가 그대로 통과한다.
4. 영어일 때는 `text`를 `textEn`으로, `speaker`를 표의 `nameEn`으로 바꾼다. 영어가 빈 줄은 그 줄만 한국어로 나온다. 대사 상자가 비지 않고, 같은 누락은 EditMode 테스트가 먼저 실패로 보여 준다.

필수 단계에서 바꾸지 않는 파일: `DialogueProgress.cs`, `DialogueView.cs`, `StartView.cs`, `StartPresenter.cs`, `UiLayer.cs`, `UIRoot.cs`, 게임 상태 코드(Core), Scene 2개, 프리팹, 패키지, asmdef.

### 영어판을 띄우는 방법(버튼이 없을 때)

- 에디터: `DialogueSequence.asset`의 Default Language를 `English`로 바꾸면 다음 대화부터 영어가 나온다. Play 중에 바꾼 에셋 값은 디스크에 남으므로 시연 뒤 `git status`로 확인하고 되돌린다.
- 빌드: 값을 `English`로 바꾼 상태로 빌드를 하나 더 만든다. 그 값은 커밋하지 않는다.
- 빌드 하나로 두 언어를 쓰려면 실행 인자(`-rebootLang en`)를 읽는 처리를 더할 수 있다. 약 1시간으로 보지만 이 계획의 필수 단계에는 넣지 않았다.

### 대사 변형과의 관계

`05` 문서의 선택 사항(성과에 따른 마무리 변형, 4.4)이 들어와도 순서는 '변형 선택 → 언어 해석 → 진행 시작'이다. 변형 선택은 언어와 무관하고, 통계는 Finishing이 끝날 때 닫히므로 마무리 대화에 들어올 때 두 입력이 모두 정해져 있다.

- 병합 순서는 한국어 대사 교체(`05` 문서 7절의 1번) → 이 문서의 필수 단계 → 마무리 변형(`05` 문서 4.4)이다. 같은 에셋과 같은 코드 줄(`DialoguePresenter.cs` 32행, `DialogueSequenceData.cs`)을 고치므로 두 작업을 동시에 하지 않는다.
- 변형이 먼저 병합되면 영어 입력은 10줄에서 22줄로 늘어난다(기본 10, 변형 두 묶음 12).
- 변형과 기본이 공유하는 줄(첫 줄, 끝 두 줄)은 `text`뿐 아니라 `textEn`, `speaker`, `leftSpeaker`도 같아야 하고 자료 테스트가 이를 본다.
- Retry 뒤에도 남기는 값(버튼을 만들 때의 언어 선택)은 static에 두지 않는다. 씬을 다시 읽으면 처음 상태로 돌아가야 PlayMode 테스트가 실행 순서에 의존하지 않는다.

## 4. Start 화면의 선택 버튼(선택 단계)

빌드 하나로 두 언어를 번갈아 보여 줘야 할 때만 만든다. 필수 단계가 병합되고 발표 전의 다른 일이 끝난 뒤에 시작한다.

- 위치: Start 화면 오른쪽 위. 모양은 `DIALOGUE  KOR | ENG`이고, 고른 칸은 청록색 글자와 밑줄, 다른 칸은 흐린 색이다.
- `LANGUAGE`가 아니라 `DIALOGUE`라고 적는다. UI 라벨은 두 언어에서 같고 대사만 바뀌기 때문이다.
- 버튼 두 개다. 칸을 누르면 그 언어가 된다. 같은 칸을 다시 눌러도, 더블클릭해도 값이 뒤집히지 않는다.
- 두 버튼은 `Navigation.Mode.None`, `Transition.None`으로 만든다. 씬의 UI 입력은 WASD와 방향키로 선택을 옮기고 Enter로 누르게 돼 있어서, 그대로 두면 키보드로 언어가 바뀔 수 있다. 설정을 읽고 판단한 것이며 재현해 보지는 않았다.
- 프리팹에 저장하지 않고 `StartView.OnEnable`에서 한 번 만든다. 팀 프리팹 빌더가 Start 프리팹의 자식을 모두 지우고 다시 만들기 때문이다(같은 방식의 선례: `DialogueView.EnsureAdvanceArea`, `CountdownView.EnsureFlash`).
- 강조와 숨김은 `StartPresenter`가 Ready에 들어올 때 현재 설정으로 맞춘다. View의 첫 `OnEnable`이 Presenter 생성보다 늦기 때문이다. 에셋을 읽지 못하면 버튼을 숨긴다.
- 버튼은 게임 상태를 바꾸지 않고 설정 값만 바꾸므로 요청을 보내지 않는다. Retry 확인창을 열고 닫는 기존 처리와 같은 방식이다.
- 키보드 단축키는 넣지 않는다. 키 배치는 팀 미확정 항목이다.

오른쪽 위에 두는 이유는 Start 화면으로 넘어오는 화면(Pause, Retry 확인창, Result)의 버튼이 그 자리에 없어서다. START 버튼 바로 아래는 Pause 화면의 QUIT TO START 버튼 자리라서, 거기에 두면 QUIT을 두 번 누를 때 두 번째 클릭이 언어를 바꿀 수 있다. 대화 화면의 SKIP과는 같은 자리지만 SKIP을 누르면 Countdown으로 가므로 연달아 누른 클릭이 이 버튼에 닿지 않는다.

### 고른 언어의 유지

- 고른 언어는 한 번 실행한 동안 유지한다. Retry와 Quit to Start 뒤에도 남고, 게임을 다시 켜면 기본값으로 돌아간다.
- 디스크(`PlayerPrefs`)에 저장하지 않는다. 저장하면 에디터에서 직접 플레이하며 고른 언어가 PlayMode 테스트에도 적용되어 같은 테스트의 결과가 컴퓨터마다 달라진다.
- 언어는 라운드 상태가 아니라 플레이어 설정으로 본다. AGENTS.md 12절이 Reset 뒤에 남으면 안 되는 것으로 든 목록(Score, Gauge, Rigidbody 속도, 적, 투사체, 예약 이벤트)에 언어는 없다. 다만 17절의 '최초 실행과 동일한 초기 조건'을 라운드 상태에만 적용한다는 해석이므로 팀 확인 항목에 올린다(9절).
- 팀이 유지하지 않기로 정하면 `UIRoot.ResetRound`에서 설정을 기본 언어로 되돌리는 한 줄을 넣는다. 그 밖의 코드는 같다.

## 5. 대사 작성 규칙과 검증

아래 테스트는 아직 없다. 이 계획에서 새로 만든다.

작성 규칙:

- 줄 하나에 두 언어를 함께 채운다.
- 영어 칸에는 ASCII 인쇄 문자(U+0020~U+007E)만 넣는다. 문서 편집기에서 붙여 넣으면 둥근 따옴표와 긴 줄표가 섞인다. 이 글자들은 대화 글꼴에 있어서 경고 없이 나오고 곧은 따옴표와 섞여 보인다. 아포스트로피는 Inspector에서 직접 친다.
- 본문에 `<`와 역슬래시를 넣지 않는다. 대사 본문은 서식 태그와 역슬래시 시퀀스를 해석하도록 설정돼 있다(`Dialogue.prefab`의 `m_isRichText`, `m_parseCtrlCharacters`). `<b>` 같은 태그나 `\n`, `\t` 같은 시퀀스가 들어가면 타이핑이 세는 글자 수와 화면 글자 수가 달라진다.
- 본문에 줄바꿈과 탭을 넣지 않는다. 글자 수는 어긋나지 않지만 2행 중 한 행을 쓰게 된다. 2절의 다를 고를 때만 줄바꿈을 쓴다.
- 한국어 줄은 한 행(약 44자 이하)을 권한다. 대사 상자는 2행까지 보이지만, 한국어가 2행으로 넘어가면 어절 중간에서 줄이 바뀐다(TMP Settings의 한글 줄바꿈 규칙이 꺼져 있다).
- 에셋은 Inspector에서 고친다. YAML은 한글을 `\uXXXX`로 저장해 손으로 고치기 어렵다. Inspector의 Reset은 쓰지 않는다. 코드 기본값으로 덮인다.
- 한국어 줄을 고치면 같은 줄의 영어도 확인한다. 낡은 번역은 자동으로 잡지 못한다.

필수 단계에서 쓸 테스트:

| 테스트 | 종류 | 보는 것 |
| --- | --- | --- |
| `DialogueLocalizerTests.KoreanResolveKeepsSpeakerTextAndSide` | EditMode | 한국어 해석은 화자, 본문, 좌우를 글자까지 그대로 둔다 |
| `DialogueLocalizerTests.EnglishResolveUsesTextEnAndSpeakerName` | EditMode | 영어 해석은 본문과 화자 이름을 바꾸고 좌우와 줄 수는 그대로 둔다 |
| `DialogueLocalizerTests.EnglishResolveFallsBackToKoreanWhenEmpty` | EditMode | 영어가 비었거나 화자가 표에 없으면 그 값만 한국어로 나온다 |
| `DialogueLocalizerTests.ResolveReturnsCopyAndKeepsSource` | EditMode | 결과는 새 배열이고 에셋의 배열은 바뀌지 않는다 |
| `DialogueSequenceDataTests.ShippedSequenceHasNoBilingualProblems` | EditMode | 실제 에셋의 모든 줄에 영어가 있고, 화자마다 영어 이름이 있고, 영어 칸이 ASCII뿐이고, `<`와 역슬래시가 없다 |
| `DialogueSequenceDataTests.DefaultSequenceHasNoBilingualProblems` | EditMode | 코드 기본값도 같은 검사를 통과한다 |
| `DialogueLanguageSceneTests.EnglishDefaultDrivesIntroAndOutroAndEveryLineFits` | PlayMode | 씬을 읽기 전에 기본 언어를 `English`로 바꾸고(끝나면 되돌린다) 도입과 마무리가 영어로 나오는지, 글꼴이 같은지 본다. 두 언어의 모든 줄을 실제 대사 상자에 넣어 2행 이내, 잘림 없음, 글자 수 일치, 글꼴에 없는 글자 없음을 본다 |

- 글꼴 검사는 `font.HasCharacters(text, out uint[] missing, searchFallbacks: false, tryAddCharacter: true)`로 한다. 다른 오버로드는 이미 아틀라스에 올라온 글자만 보므로 실행 중 만든 동적 폰트에서는 거짓 실패가 난다.
- 에셋 값을 씬 로드 전에 바꾸고 끝에서 되돌리는 방식은 기존 테스트에 선례가 있다(`CombatRoundSceneTests.cs` 203~239행).
- 기존 테스트는 고치지 않는다. 화면 글자를 에셋과 비교하는 기존 테스트는 `DialogueAdvancesSkipsAndRestartsAfterRetry` 하나이고, 기본 언어가 한국어인 동안 그대로 통과한다. 기본 언어를 영어로 바꿔 커밋할 일이 생기면 그 테스트에 한국어 고정(SetUp과 TearDown)을 더한다.
- 현재 기준선은 EditMode 76개, PlayMode 18개다. PlayMode에는 이전부터 흔들리는 팀 테스트 `AcceptedHitUpdatesHudAndRetryClearsRound`가 있다. 이 테스트만 실패하면 그것만 다시 돌린다.
- Unity가 없는 사람은 `05` 문서 3절의 표로 대사를 검토한다.

## 7. 줄이면 안 되는 것

- 번역 누락을 막는 EditMode 에셋 테스트와, 실제 대사 상자에서 2행과 잘림을 보는 PlayMode 테스트
- 한국어 해석이 문자열을 그대로 복사하는 것(기존 테스트가 여기에 기댄다)
- 에셋이 없어도 예외가 나지 않는 것(`_data`가 `null`인 경로)
- 버튼을 만든다면: 버튼 두 개 구조, 오른쪽 위 위치, 키보드 이동 끄기

시간이 모자라면 선택 단계 전체를 발표 뒤로 미룬다. 필수 단계도 어렵다면 가(영어 에셋 교체)로 한 번 보여 준다.

## 8. 범위 밖: UI 라벨의 한국어화

지금은 하지 않는다. 대략 12~16시간이 더 들 것으로 보고, 발표 직전에 하기에는 위험이 크다.

- Chakra Petch에 한글이 없어 대체 글꼴 설정이 필요하다. UI 라벨은 굵게 쓰는데 한글 글꼴은 Regular만 있다.
- 한국어 라벨은 폭이 달라 화면 8개의 배치를 다시 확인해야 한다.
- 대체 글꼴의 글자는 TMP가 하위 메시로 따로 그린다. 투명도를 직접 바꾸는 연출이 하위 메시까지 맞추는지 확인해야 한다. 굵은 글자의 하위 메시에 투명도가 전달되지 않아 카운트다운 숫자가 옅게 보이던 결함(`CountdownView.cs`, 커밋 전 수정)이 같은 종류였다.

## 9. 위험과 팀이 정할 것

| 위험 | 대응 |
| --- | --- |
| 영어 문장과 노아의 영어 표기가 확정되지 않았다 | 에셋과 문서에 임시값으로 표시한다. 확정은 에셋만 고치면 된다 |
| 한국어를 고치고 영어를 그대로 두는 낡은 번역 | 두 언어가 같은 줄에 붙어 있다. 발표 전에 `05` 문서의 표와 에셋을 한 번 대조한다 |
| 에셋 YAML의 한국어 diff와 병합 충돌을 읽을 수 없다 | 에셋은 한 번에 한 사람만 고친다 |
| 기존 에셋에 새 칸을 더했을 때 값이 어떻게 읽히는지 실행해 보지 않았다 | 1단계 뒤 에셋을 Inspector로 열어 새 칸이 보이고 한국어 10줄이 그대로인지 본다. 값 하나를 고쳐 저장하고 `git diff`가 줄 추가뿐인지 본다. 한국어 줄이 바뀌었으면 되돌린다 |
| 한 실행에서 두 언어를 모두 재생하면 동적 글꼴 아틀라스가 한 장을 넘는 것으로 계산된다 | 여러 장 쓰기가 기본으로 켜져 있어 동작할 것으로 본다. 5단계의 수동 확인에서 글자 누락이 없는지 본다 |
| (버튼) 팀 프리팹 빌더를 다시 돌리면 Start 프리팹의 자식이 모두 지워지고 다시 만들어진다 | 버튼을 프리팹에 저장하지 않고 실행 중에 만든다 |
| (버튼) 꺼져 있는 화면의 버튼 위치를 테스트가 읽을 수 있는지 모른다 | 읽히지 않으면 겹침 단언을 빼고 수동 확인으로 대신한다 |

함께 발견한 것(이 계획과 무관, 고치지 않음): Pause의 QUIT TO START 버튼은 위쪽 44px이 Start 화면의 START 버튼과 같은 자리다. Retry 확인창의 RESTART 버튼은 가로 160px, 세로 82px이 START 버튼과 겹친다(1920×1080 프리팹 좌표로 계산). 빠르게 두 번 누르면 두 번째 클릭이 바로 게임을 시작시킬 수 있다. 재현해 보지는 않았다.

영어 화면에서 하나 더 걸린 것이 있다. Result 화면의 라벨 `SPECIAL USE`다. 영어 대본을 처음 읽게 한 검토에서 두 번 모두 '특별한 용도'처럼 읽힌다는 지적이 나왔다. 옆의 `HITS TAKEN`과 같은 꼴인 `SPECIALS USED`가 제안됐다. UI 담당이 정한다.

팀이 정할 것:

1. 영어판이 어디에 필요한지(영어로 한 번 보여 주기, 빌드 하나로 번갈아 보여 주기, 두 언어 사용자가 함께 보기). 이것이 2절의 방법을 가른다.
2. 2절의 방법 가운데 무엇으로 갈지. 권장은 나의 필수 단계다.
3. 영어 대사의 최종 문장과 확정 기한. 영어를 잘 쓰는 사람의 확인을 받을지. 노아의 영어 표기는 `05` 문서 9절에서 정한다.
4. 기본 언어. 제안은 한국어다.
5. 발표를 에디터로 할지 빌드로 할지. 빌드라면 최종 확인을 빌드에서 한다.
6. 구현 브랜치와 `main` 통합 방법. `main`은 `0093036` 계열과 공통 조상이 없다.
7. (버튼을 만든다면) Start 화면에 선택 버튼을 더해도 되는지. AGENTS.md 11절과 UI 설계 5절은 Ready 화면을 Overlay, 중앙 Start 버튼, 제목과 조작 안내로 적었다.
8. (버튼을 만든다면) 고른 언어를 Retry와 Quit to Start 뒤에도 유지할지. 제안은 유지다.

## 10. 확인한 범위

- **Unity에서 잰 것**: `05` 문서의 대사(기본 10줄, 변형, 대체 문구)를 `Main.unity`의 실제 대사 상자에 한국어와 영어로 넣었다. 모든 줄이 한 행이고 잘리지 않았으며 글꼴에 없는 글자가 없었다. 한국어와 영어를 줄바꿈으로 이은 문자열은 2행에 들어가고 TMP가 센 글자 수가 문자열 길이와 같았다. 화자 이름 `Noa`와 `노아 / Noa`도 한 행이다. 측정용 임시 테스트는 지웠다.
- **코드와 설정을 읽어 확인한 것**: `DialogueSequenceData.cs`의 구조, `DialoguePresenter.cs` 32·45·89~90행, `UiLayer` 생성자와 `UIRoot.Configure`의 호출 관계, `Dialogue.prefab` 본문의 서식·역슬래시 해석 설정, 프리팹 좌표, 테스트 어셈블리의 참조(EditMode에는 TMP가 없고 PlayMode에는 있다), TMP 패키지 소스(줄바꿈 문자는 한 글자로 센다, `HasCharacters` 오버로드).
- **실행하지 않은 것**: 이 계획의 코드와 테스트 전부, 빌드에서의 영어 표시, 키보드로 버튼이 눌리는지, 버튼 두 번 클릭의 재현. 시간은 모두 추정이다.
- **만든 방법**: AI 도구로 구조가 다른 초안 둘(언어별 에셋, 줄마다 영어 칸)을 만들어 견주고 뒤쪽을 골랐다. 그 뒤 코드 대조와 반론 검토를 거쳐 권장 범위를 버튼 포함 15시간에서 필수 6.5시간으로 줄였다. 팀원이나 영어 화자가 검토한 것은 아니다.
