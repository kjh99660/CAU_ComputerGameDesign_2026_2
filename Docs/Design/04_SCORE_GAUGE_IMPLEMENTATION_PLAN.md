# 점수, 특수 게이지 및 라운드 결과 구현 계획

> 상태: 구현 전 계획
>
> 기준 확인일: 2026년 11월 3일
>
> 범위: 점수와 특수 게이지, 전투 통계, HUD와 결과 화면의 데이터 연결

플레이어가 적을 공격하거나 피격될 때 점수와 게이지가 바뀌고, 제한 시간이 끝난 뒤 결과 화면에 한 라운드의 기록이 표시되도록 한다. 점수와 게이지 관련 수치는 Unity Inspector에서 조정할 수 있도록 한곳에 모은다. 전투 판정, UI, 재시작은 기존 시스템을 이용하며, 팀에서 확정하지 않은 수치는 임시값으로 표시한다.

## 2. 구현 결과와 범위

### 이번 작업에서 연결할 기능

1. 공격 적중과 적 처치가 확인되면 설정값에 따라 점수와 게이지를 반영한다.
2. 플레이어 피격이 유효하면 현재 점수의 10%를 감점하고 게이지를 증가시킨다. 피격 무적의 기본 시간은 0.8초다.
3. 현재 점수, 남은 시간과 게이지를 전투 HUD에 표시한다.
4. 라운드가 끝나면 최종 점수, 처치 수, 최대 콤보, 플레이어 피격 수, 특수 스킬 사용 횟수를 결과 화면에 표시한다.
5. Pause, Finishing, Retry에 맞춰 점수 수용과 초기화를 제어한다.
6. 수치 설정, 점수 계산, 중복 방지와 Reset을 자동 테스트하고 실제 Scene 흐름을 검수한다.

### 연동 범위를 구분할 기능

- 적중·피격 이벤트가 아직 없다면 점수 기능을 검증할 수 있는 최소 판정 연결을 추가한다. 공격 모션, 무기 모델, 적 AI 전체를 재구성하지 않는다.
- 특수 스킬의 게이지 확인·차감과 사용 횟수를 연결할 수 있는 진입점은 만든다. 스킬 동작 자체가 없는 경우에는 팀의 스킬 구현과 연결할 지점으로 남기고 완료된 기능으로 보고하지 않는다.
- 타이머와 Finishing은 점수 확정에 필요한 범위에서 기존 구현을 보완한다. 대사와 전투 콘텐츠 전체를 새로 만드는 작업은 포함하지 않는다.
- Player HP, Enemy HP Bar, Damage Number, Aim Assist와 Lock-on은 추가하지 않는다.

## 3. 조정 가능한 수치

점수와 게이지 설정은 `ScriptableObject` 자산으로 모아 Inspector에서 변경할 수 있게 한다. 아래 제안값은 밸런스 확정값이 아니다. 설정을 변경한 뒤 에디터에서 다시 실행하거나 빌드에 반영한다.

| 설정 | 초기값 | 상태 및 용도 |
| --- | ---: | --- |
| 일반 공격 적중 점수 | 10 | 제안서의 임시값 |
| 적 처치 점수 | 100 | 제안서의 임시값 |
| 일반 공격 적중 게이지 | 3 | 적 한 명당 임시값 |
| 적 처치 게이지 | 5 | 적 한 명당 임시값 |
| 플레이어 피격 게이지 | 8 | 유효한 피격 한 번당 임시값 |
| 게이지 최대치 | 100 | 임시값 |
| 플레이어 피격 점수 감소율 | 10% | 현재 확정 규칙. 설정으로 노출하되 변경은 팀 합의 후 반영 |
| 피격 무적 시간 | 0.8초 | 기본값, 조정 가능 |
| 콤보 입력 시간 | 0.4초 | 기본값. 현재 플레이어의 애니메이션 비율 기반 입력 구간과 관계를 확인해 적용 |
| 스킬 사용 조건과 소모량 | 미확정 | 팀 결정 후 설정값 연결 |
| 점수 콤보의 유지 조건과 배율 | 미확정 | 공격 입력 콤보와 구분하여 팀 결정 후 설정 |

설정에는 음수나 게이지 최대치 0과 같은 잘못된 값이 들어가지 않도록 Inspector 검증을 둔다. 점수 감점 시 소수점 처리 방식은 팀 합의가 필요하다. 합의 전 임시 정책을 사용한다면 코드와 테스트에 명시한다. 점수는 0 미만으로 내려가지 않게 하고, 게이지는 0과 최대치 사이로 제한한다.

예를 들어 위 임시값에서 일반 공격으로 적 한 명을 유효하게 맞혀 처치하면 적중 점수 10과 처치 점수 100을 더해 110점, 게이지 3과 5를 더해 8을 얻는다. 실제 적용 수치는 팀 테스트에서 조정한다.

## 4. 데이터 흐름과 책임

```text
플레이어 공격 / 적 공격
        ↓ 유효 판정과 라운드 Tick 확인
적중·처치·피격·스킬 사용 결과
        ↓
라운드 점수·게이지·통계 소유 시스템
        ↓ 값이 바뀔 때만 알림
Battle HUD / Finishing HUD / Result 화면
```

| 구성 | 책임 |
| --- | --- |
| 전투 설정 자산 | 점수, 게이지, 무적 시간 등 조정할 값을 제공한다. |
| 공격·피격 판정 연결 | 유효한 판정 결과와 해당 라운드의 `Tick`을 전달한다. 점수나 UI를 직접 수정하지 않는다. |
| 라운드 전투 기록 | 점수, 게이지, 처치 수, 콤보, 피격 수와 스킬 사용 횟수를 한곳에서 소유한다. 설정과 판정 결과를 받아 값을 계산한다. |
| UI Presenter와 View | 전투 기록의 변경을 받아 화면을 갱신한다. 화면에 표시된 숫자를 실제 점수의 원본으로 사용하지 않는다. |
| 초기화·Reset Coordinator | 전투 기록 참여자의 초기화와 Reset 완료를 기다린다. 기존 참가자 등록과 완료 절차를 확장한다. |
| GameStateManager | 기존처럼 상태와 `Tick`을 소유한다. 점수 계산과 개별 전투 객체 제어는 맡지 않는다. |

점수 계산은 Unity 화면과 분리해 테스트할 수 있는 일반 C# 로직으로 두고, Scene 연결과 생명주기는 Unity 컴포넌트가 맡는다. 기존 `GameDemo.Core`와 `GameDemo.Systems`의 참조 방향을 유지하고, 같은 책임의 관리자를 중복 생성하지 않는다. 클래스명과 파일 경로는 작업 브랜치의 실제 구조에 맞춰 확정한다.

게임 상태 변경 요청은 기존 요청 큐에서 다음 프레임에 처리한다. 유효 판정과 그에 따른 점수·게이지 변경 알림은 상태 변경 요청과 구분하고, 현재 라운드의 `Tick`을 검증한다. 상태 변경 알림을 요청 큐에 다시 넣거나 UI에서 상태를 직접 바꾸지 않는다.

## 5. 적중과 피격 처리

### 플레이어가 적을 공격할 때

1. 공격의 유효 구간에 들어온 적을 확인하고 현재 `Tick`과 공격 식별 정보를 전달한다.
2. 기존 `EnemyRuntime.TryApplyHit`가 유효한 타격을 받아들인 경우에만 적중 결과를 발행한다.
3. 적은 한 번의 유효 타격으로 사망하므로, 인정된 타격에 대해 적중과 처치를 각각 한 번 반영한다. 넉백·사망 연출과 Pool 반환이 뒤따라도 처치 보상을 다시 지급하지 않는다.
4. 하나의 공격이 같은 적에 여러 번 닿아도 중복 반영하지 않는다. Pool에서 재사용된 적은 이전 생명주기의 판정 기록과 구분한다.

### 플레이어가 피격될 때

1. 피격이 가능한 상태인지, 이전 피격의 무적 시간이 끝났는지 확인한다.
2. 유효한 피격 한 번당 점수를 감점하고 게이지와 피격 횟수를 갱신한다.
3. 피격 무적 중 들어온 중복 판정은 점수와 통계에 반영하지 않는다.
4. 예를 들어 점수가 150일 때 유효한 피격을 한 번 받으면 15점이 감소해 135점이 된다.

공격 유효 구간, 충돌 범위와 입력 처리의 소유자는 기존 플레이어·적 담당 코드와 맞춘다. 임시 디버그 입력은 검증 보조 수단으로만 사용하고 실제 판정 연결 여부와 구별한다.

## 6. 상태, 시간과 결과 확정

| 상태 | 점수와 게이지 처리 |
| --- | --- |
| Ready / IntroDialogue / Countdown | 전투 판정과 점수 변경을 받지 않는다. |
| Battle | 유효한 공격·피격·스킬 결과를 받는다. 타이머는 100초에서 시작한다. |
| Paused | 새 판정과 점수·게이지 변경을 중지한다. Resume 시 기존 기록을 유지한다. |
| Finishing | 시간 종료 전에 시작한 공격의 적중과 처치, 이미 진행 중인 피격 결과를 정산한다. 새 공격·이동 명령과 AI 판단·스폰은 막는다. |
| OutroDialogue / Result | 점수 수용 창을 닫는다. 결과 화면에는 확정된 기록을 표시한다. |

타이머가 0이 되는 순간 새 전투 명령을 즉시 막고 `TimerReachedZero` 요청을 발행한다. 상태 전환은 기존 큐 규칙대로 다음 프레임에 처리한다. 현재 UI가 직접 시간을 감소시키는 경로는 제거하고, 타이머 소유자를 한곳으로 정해 UI는 값을 표시하도록 바꾼다.

Finishing에서는 실제 시간 기준 기본 2.5초 동안 `Time.timeScale = 0.5`를 적용한다. 공격이 시간 종료 전에 시작됐는지 식별할 수 있는 정보를 유지해, 같은 `Tick`이라는 이유만으로 종료 후 새로 시작한 공격을 허용하지 않는다. 정산이 끝나는 순간 점수 수용 창을 닫고 `Time.timeScale`을 1.0으로 복구한 뒤 `FinishingCompleteRequest`를 발행해 OutroDialogue로 이어간다. 정상 종료뿐 아니라 Reset과 예상 밖의 상태 이탈에도 복구 경로를 둔다.

Battle 타이머가 추후 Hit Stop의 영향을 받는지는 팀에서 결정한다. 이 결정과 관계없이 Finishing 지속시간은 unscaled time으로 측정한다.

## 7. 초기화와 Retry

전투 기록 시스템은 기존 초기화와 Reset 참가자로 등록한다. Reset 요청을 수락하면 생산자를 먼저 멈추고 새 `Tick`을 받은 뒤 점수, 게이지, 콤보, 처치·피격·스킬 통계와 남은 판정 기록을 초기화한다. 기존 라운드의 지연 판정과 콜백은 새 `Tick`에서 무시한다. 전투 기록이 초기화된 다음 UI를 동기화하도록 참가자의 실행 순서 또는 완료 Barrier를 구성한다. 모든 참가자가 준비됐다는 보고가 끝난 뒤에만 Ready 화면을 표시한다.

- Pause Retry: 확인 모달에서 승인한 경우에만 Reset한다. 취소하면 Paused를 유지한다.
- Result Retry: 확인 모달 없이 Reset 후 Start 화면으로 돌아간다.
- Pause Quit: 확인 모달과 애플리케이션 종료 없이 Reset 후 Start 화면으로 돌아간다.
- 세 경로 모두 Scene을 Reload하지 않는다. 다음 Start 이후 Intro Dialogue와 Skip을 다시 사용할 수 있어야 한다.

## 8. UI 연결

- `BattlePresenter`와 `BattleView`는 실제 점수와 남은 시간, 0~1로 정규화한 게이지를 표시한다. 현재 모델에만 있고 표시되지 않는 게이지 연결을 완성한다.
- `FinishingPresenter`와 `FinishingView`는 마감 전까지 들어온 점수 변경을 표시한다. Pause와 게이지를 숨기고 Timer 0과 TIME UP을 유지한다.
- `ResultPresenter`와 `ResultView`는 확정된 결과를 받는다. 결과가 표시된 뒤 지연 이벤트로 숫자가 바뀌지 않아야 한다.
- 화면이 처음 열리거나 Reset된 직후에는 최신 기록을 한 번 동기화하고, 이후에는 값이 변경될 때 갱신한다. 이벤트 등록과 해제는 쌍으로 관리한다.
- 점수 변화 연출을 추가할 경우 반복 요소는 Pool을 사용한다. Damage Number는 표시하지 않는다.
- 기존 Scene과 Prefab의 참조 및 `.meta` GUID를 보존하고, Prefab을 통째로 재생성하는 Editor 도구는 변경 내용을 확인하기 전에는 사용하지 않는다.

## 9. 구현 순서

각 단계는 컴파일과 해당 테스트를 확인한 뒤 다음 단계로 진행한다.

| 단계 | 작업 | 완료 확인 |
| --- | --- | --- |
| 1 | 기준 브랜치와 필요한 에셋을 확인하고 기존 테스트를 실행한다. | 작업 기준과 누락 에셋을 정하고, 기존 실패의 재현 조건을 확인한다. |
| 2 | 설정 자산과 점수·게이지·통계 계산을 만든다. | Inspector에서 값을 바꾸고 계산 테스트를 통과한다. |
| 3 | 적중·처치·피격 결과와 기존 Enemy/Player를 연결한다. | 유효한 판정 한 번이 점수와 통계에 한 번만 반영된다. |
| 4 | HUD와 Result에 기록을 연결하고 타이머의 단일 소유자를 정한다. | Battle, Finishing, Result에서 각각 올바른 값이 보인다. |
| 5 | Finishing 점수 마감과 Reset 참가를 연결한다. | 시간 종료 전 공격의 결과가 반영되고 Retry 후 모든 기록이 초기화된다. |
| 6 | Play Mode와 실제 게임 화면, 플랫폼별 빌드를 확인한다. | 실패 항목과 재현 방법을 기록하고 수정 범위를 정한다. |

점수·게이지 범위의 잠정 작업량은 약 10~22시간이다. 플레이어와 적의 기존 판정에 연결할 수 있다는 가정이며, 특수 스킬 전체 제작, 에셋 복구, 타 플랫폼의 성능 최적화, 라이선스 문제 해결 시간은 별도다.

## 10. 검수 계획

### Edit Mode

- 설정값을 변경하면 적중, 처치, 피격의 점수와 게이지가 설정대로 반영된다.
- 10% 감점과 소수점 처리, 점수 0 하한, 게이지 상·하한이 일관된다.
- 한 번의 유효 타격과 반복 충돌, 적 Pool 재사용에서 처치가 중복 집계되지 않는다.
- 피격 무적 시간과 현재 라운드가 아닌 `Tick`의 이벤트를 검증한다.
- 동일 Reset을 여러 번 요청해도 점수와 통계가 같은 초기값으로 남는다.

### Play Mode와 실제 화면

1. Start → Intro Dialogue 또는 Skip → Countdown → Battle을 진행한다.
2. 적을 공격하고 플레이어가 피격될 때 HUD, 점수와 게이지가 설정값대로 바뀌는지 확인한다.
3. Pause 중 판정과 수치가 멈추고 Resume 후 이어지는지 확인한다.
4. 100초 직전에 시작한 공격이 Finishing 중 적중하면 점수에 반영되고, 정산이 끝난 뒤의 지연 이벤트는 무시되는지 확인한다.
5. Finishing 종료와 Reset 이후 `Time.timeScale == 1.0`인지 확인한다.
6. Pause Retry 취소·승인, Pause Quit, Result Retry를 각각 확인한다. 새 라운드에 이전 점수, 게이지, 통계와 이벤트가 남지 않아야 한다.
7. 결과 화면의 점수·처치·최대 콤보·피격·스킬 사용 횟수가 한 라운드의 실제 기록과 일치하는지 확인한다.
8. 16:9와 팀이 정한 해상도에서 HUD가 겹치지 않는지 보고, 최종 발표 플랫폼에서는 해당 플랫폼의 빌드를 별도 실행한다.
9. 전투가 연결된 뒤 활성 적 100명에서 프레임과 불필요한 반복 할당을 측정한다. 200명과 300명은 별도 스트레스 설정으로 측정하고 기기와 조건을 기록한다.

팀원이 테스트를 실행할 때는 프로젝트가 다른 Unity Editor에서 열려 있지 않은지 확인한다. 아래의 `CGD_UNITY_EDITOR`와 `CGD_PROJECT_DIR`에는 각자의 경로를 넣는다. 테스트 결과는 프로젝트 밖의 임시 폴더에 남긴다.

```sh
CGD_TEST_RESULTS_DIR="$(mktemp -d "${TMPDIR:-/tmp}/game-tests.XXXXXX")"
"$CGD_UNITY_EDITOR" -batchmode -nographics -projectPath "$CGD_PROJECT_DIR" \
  -runTests -testPlatform EditMode \
  -testResults "$CGD_TEST_RESULTS_DIR/editmode.xml" \
  -logFile "$CGD_TEST_RESULTS_DIR/editmode.log"
```

Play Mode 테스트는 `-testPlatform PlayMode`로 바꾸고 결과·로그 파일을 따로 지정한다. XML의 테스트 수와 통과·실패 수를 확인하며, `-nographics` 결과만으로 실제 화면과 조작감까지 검수했다고 판단하지 않는다.

## 11. 팀과 정할 사항

- 실제 작업 기준 브랜치와 Player·Enemy·UI 담당자 간 변경 파일 조율
- 피격 감점의 소수점 처리 방식
- 점수 콤보의 성립 조건, 유지 시간과 배율
- 스킬 게이지 소모량과 스킬로 적을 처치했을 때 게이지 회복 여부
- Battle 타이머와 Hit Stop의 관계
- 발표·제출 플랫폼과 검수할 해상도, Windows 빌드 담당 장비

위 항목이 정해지기 전에는 확정되지 않은 값을 게임 규칙으로 고정하지 않는다.
