# 적 100명 공간 분할 A/B 측정 도구

작성일 2026-11-23. 브랜치 `perf/enemy-ab`(`ui/screen-effects` `0093036` 기준). 병합과 PR은 아직 하지 않았다.

적 주변 후보를 찾을 때 공간 분할(격자)을 쓰는 경우와 쓰지 않는 경우를 같은 조건에서 비교한다. 바꾸는 것은 이 한 가지뿐이다(풀링, 렌더링, 물리 설정은 그대로).

> **이 문서의 수치는 Mac에서 도구가 맞게 도는지 확인한 결과다. 시연 PC 실측이 아니다.** 시연 PC 수치는 6절 절차로 그 PC에서 직접 잰 뒤 7절 표에 따로 적는다.

## 1. 무엇을 비교하나

| | A: 공간 분할 (`SpatialGrid`, 기본·출시 구성) | B: 전수 (`BruteForce`, 비교 기준) |
| --- | --- | --- |
| 후보 | 질의 범위와 겹치는 격자 칸의 적 | 활성 적 전부 |
| 격자 유지 | 적이 움직일 때마다 갱신 | 하지 않음 |
| 거리 판정 | 같음(`EnemyAgent.CalculateSeparation`, `EnemyRuntime.ApplySpecial`) | 같음 |

격자를 쓰는 곳은 두 군데다.

- **적 분리(Separation) 이웃 검색**: 프레임마다 활성 적 한 명당 한 번, 반경 2m(`separationDistance`).
- **특수 공격 범위 판정**: 특수 공격 한 번당 한 번, 반경 6m(`specialRadius`).

일반 공격(검 휘두르기)은 `Physics.OverlapBox`로 판정하므로 이 스위치의 영향을 받지 않는다. PhysX 내부의 후보 수는 Unity가 내보내지 않아 기록하지 못한다(미지원).

"후보 수"는 정확한 거리 판정을 하기 전에 살펴본 적의 수다(자기 자신 포함).

## 2. 측정 종류 두 가지

두 종류의 수치는 서로 다른 것을 잰다. 한 표에 섞지 않는다(CSV의 `kind` 열이 `round` 또는 `micro`).

| | 실제 한 판 (`round`) | 마이크로벤치마크 (`micro`) |
| --- | --- | --- |
| 무엇이 도나 | 실제 `Main.unity`의 게임 전체(적 AI, 애니메이션, 물리, 렌더링, UI) | 후보 수집과 거리 판정 계산만 |
| 적 위치 | 게임의 AI가 움직인 결과 | 저장된 궤적을 그대로 재생(두 방식이 완전히 같은 위치) |
| 재는 시간 | 프레임마다 `EnemyRuntime.UpdateAI` 한 번에 걸린 시간 | 프레임마다 후보 수집+판정 100회에 걸린 시간 |
| 프레임 시간·FPS·Draw Call | 화면에 그리는 실행에서만 기록 | 해당 없음 |
| 쓰임 | 실제 플레이에서의 효과, 발표용 실측 | 같은 입력에서의 순수 비교, 결과 일치 확인 |

## 3. 실제 한 판의 시나리오

1. 판마다 씬을 새로 불러 같은 tick에서 시작한다. 적 생성 위치는 `7919 + tick × 104729`를 시드로 하는 난수에서 나오므로(`EnemyRuntime.PrepareRound`) 판마다 같다. 이번 실행은 tick 1, 시드 112648이다.
2. 게임 시간은 프레임당 1/60초로 고정한다(`Time.captureFramerate = 60`). 실제로 걸린 시간과 무관하게 같은 순서로 진행된다.
3. 판마다 물리 주기의 같은 지점에서 시작한다. 프레임(1/60초)과 물리 스텝(0.02초)은 6프레임마다 같은 어긋남으로 돌아오는데, 그 주기의 정해진 프레임까지 기다렸다가 시작한다. 맞았는지는 결과의 `physics_phase_ms`로 확인한다(판마다 거의 같아야 한다. 한 프레임 어긋나면 3.3ms 차이가 난다).
4. 대화와 카운트다운은 게임과 같은 요청(Request)으로 넘긴다. 입력 장치와 키 설정은 건드리지 않는다.
5. 플레이어는 시작 위치에 서 있다. 게임의 생성 규칙대로 적이 100명이 될 때까지 기다린다(1140프레임 = 19초). 적 수를 늘린 실험에서는 이 목표 수만 달라진다(5.8절).
6. 측정 구간 900프레임(15초)
   - **steady** 0~299: 공격 없음. 적 100명이 그대로다.
   - **attacks** 300~899: 300·500·700번째 프레임에 플레이어 위치로 특수 공격 범위 판정(`EnemyRuntime.ApplySpecial`, 게임의 반경·넉백 값)을 한다. 맞은 적은 죽고, 게임 규칙대로 다시 생성된다.
7. 판 순서: 검증 판 → 격자 → 전수 → 전수 → 격자(순서 효과를 줄이려는 배치).

측정 중 플레이어가 움직였거나 카메라가 돌아갔으면 `player_moved`, `camera_moved`에 1이 찍힌다. 그 판은 시나리오에서 벗어난 것이므로 쓰지 않는다. 직접 실행할 때는 측정이 끝날 때까지 키보드와 마우스를 건드리지 않는다.

### 두 방식의 위치가 같은가

- **검증 판**은 공간 분할로 한 판을 돌리면서, 실제 판정에 쓰인 질의마다 활성 적 전부를 다시 훑어 "반경 안의 적이 격자 후보에서 빠졌는지" 센다. 같은 프레임, 같은 위치에서 두 방식을 비교하므로 위치가 완전히 같다.
- **시간 판**(격자, 전수)은 방식 하나만 켜고 따로 돈다. 시드, 물리 주기, 공격 시점은 같지만 위치가 비트 단위로 같지는 않다. 밀리미터 수준으로 다르다.
  - 이웃의 밀어내기를 더하는 순서가 방식마다 달라 부동소수점 끝자리가 달라질 수 있다.
  - 같은 방식끼리도 달라진다. 적 이동이 Rigidbody 보간의 영향을 받는 기존 문제 때문이다(8절).
  - 그 결과 아슬아슬한 사건(적의 공격이 닿는 프레임 등)은 판에 따라 한 프레임 앞뒤로 갈릴 수 있다. 합계(특수 공격 적중, 처치, 피격, 점수)는 지금까지 모든 판에서 같았다(5절).
- 판 사이의 차이는 `round_comparison.csv`에 수치로 남는다. 검증 판을 기준으로 한 비교와, 첫 시간 판(`grid-1`)을 기준으로 한 비교가 함께 들어 있다. 두 방식을 직접 견주는 행은 `grid-1` 대 `brute-*`다.
- **완전히 같은 위치**에서의 비교가 필요하면 마이크로벤치마크를 본다. 검증 판의 steady 구간에서 저장한 궤적(`trace/round100.trace.txt`, 적 100명 × 300프레임, 밀리미터 정수)을 두 방식에 그대로 재생한다.

## 4. 지표와 유효성

| 지표 | 열 | 유효한 환경 |
| --- | --- | --- |
| 후보 수, 질의 수 | `ai_candidates*`, `special_candidates` | 어디서나(세는 값이라 기기 성능과 무관) |
| CPU 시간 | `ai_cpu_us_*`, `cpu_us_per_frame_*` | 어디서나. 단, **그 기기에서 그 실행 방식으로 잰 값**이다. `Stopwatch`로 해당 코드 구간만 잰다 |
| 프레임 시간, FPS | `frame_ms_*`, `fps_from_avg_frame` | 화면에 그려 내보내는 실행(Editor Play Mode, 플레이어)만. 배치 실행은 미지원 |
| Draw Call, Batch, SetPass | `draw_calls_avg` 등 | 위와 같고, 렌더 카운터가 제공되는 빌드만 |
| 판정 일치 | `shadow_*`, `results_equal_between_modes`, `round_comparison.csv` | 어디서나 |

- 유효하지 않은 값은 **빈칸**으로 두고, `*_valid` 열에 0, `unsupported_note` 열에 이유를 적는다. 0으로 채우지 않는다.
- 환경은 `round_environment.csv`, `micro_environment.csv`에 남는다(기기 모델, CPU, GPU, OS, Unity 버전, Editor/플레이어, 배치 여부, 스크립팅 백엔드, 화면 크기). 컴퓨터 이름과 사용자 이름은 기록하지 않는다.
- 측정 중에는 수직 동기와 프레임 제한을 끄고 백그라운드 실행을 켠다(`vSyncCount = 0`, `targetFrameRate = -1`, `runInBackground = true`). 실행 중의 값만 바꾸고 끝나면 되돌린다. 프로젝트 설정 파일은 바꾸지 않는다.
- 프레임 시간은 프레임 사이에 실제로 흐른 시간이다. `fps_from_avg_frame`은 평균 프레임 시간의 역수다. 수직 동기를 끈 상태의 값이므로 평소 화면에서 보는 FPS와 다르다.
- 측정 중 게임 창이 포커스를 잃으면 그 판의 프레임 시간·FPS·Draw Call은 비우고 이유를 적는다. 후보 수와 CPU 시간은 남긴다.
- Draw Call·Batch·SetPass는 Unity Profiler의 렌더 카운터(`Draw Calls Count`, `Batches Count`, `SetPass Calls Count`)에서 읽는다. 프레임별 값(`round_frames_*.csv`)은 어떤 프레임에 0이고 그 앞 프레임에 두 프레임치가 합쳐져 나오는 경우가 있다(렌더 스레드와 게임 프레임의 경계가 어긋나기 때문으로 보인다). 합은 보존되므로 구간 평균(`*_avg`)으로 본다.
- 검증 판은 전수 비교 비용이 섞이므로 CPU 시간과 프레임 시간을 기록하지 않는다.
- Editor Play Mode의 프레임 시간에는 Editor 자체의 부하가 섞인다. 발표용 FPS는 플레이어 빌드로 잰다.

### 5.3 판정 일치

- **검증 판(같은 위치에서 질의마다 비교)**: 질의 55,414건, 반경 안의 적 200,905명.
  - 특수 공격 판정: 격자가 놓친 적 0명.
  - 분리 이웃 검색: 격자가 놓친 적 **1명**(steady 구간 272번째 프레임, 질의 1건). 넉백 중인 적은 아니었고, 격자에 기록한 뒤 Transform이 0.058m(한 프레임 이동 거리) 옮겨져 있었다. 원인은 8절.
  - 나머지 세 실행의 검증 판에서도 같은 프레임에서 같은 한 건이 나왔다(질의 55,414건, 특수 공격 0명). 우연이 아니라 이 시나리오에서 되풀이되는 일이다.
- **판 사이 비교(따로 돈 다섯 판)**: 네 실행 모두 `round_comparison.csv`의 21행 전부에서 프레임별 적 수, 특수 공격마다의 적중 수, 처치 95, 피격 6, 최종 점수 10,450이 같았다.
  - 위치는 밀리미터 해시로는 첫 프레임부터 달랐다. 적과 플레이어 사이 평균 거리의 차이는 Editor 배치에서 steady 구간 최대 7.3mm, 전체 최대 23.6mm였다(플레이어 배치 8.7mm / 41.0mm, 플레이어 창 실행 7.8mm / 24.5mm, Editor Play Mode는 Editor 배치와 같음).
  - 두 방식의 직접 비교(`grid-1` 대 `brute-1`, `brute-2`)는 Editor 배치에서 전체 구간 5.6mm, 4.4mm였다.
  - 플레이어가 맞는 여섯 번 가운데 세 번은 판에 따라 한 프레임 앞뒤로 갈렸다(73·184·295번째 또는 74·185·296번째 프레임). 네 실행의 스무 판을 보면, 전수 판 여덟 번은 모두 뒤쪽이었고 격자 판 열두 번(검증 판 포함)은 앞쪽 여섯 번, 뒤쪽 여섯 번이었다. 격자 방식은 같은 방식끼리도 갈린다. 격자 칸 안의 순서가 판마다 달라 이웃을 더하는 순서가 달라지기 때문으로 보이지만 확인하지는 않았다.

## 6. 다시 돌리는 방법

`$UNITY`는 Unity 6000.3.24f1 실행 파일이다(Mac: `/Applications/Unity/Hub/Editor/6000.3.24f1/Unity.app/Contents/MacOS/Unity`, Windows: `C:\Program Files\Unity\Hub\Editor\6000.3.24f1\Editor\Unity.exe`). 프로젝트 폴더에서 실행하고, 같은 프로젝트를 Unity Editor로 열어 둔 상태에서는 배치 명령을 쓰지 않는다. `-rebootLabel`에는 어느 기기·어떤 실행인지 알 수 있는 이름을 적는다.

```bash
# 테스트 (EditMode: 순수 규칙과 마이크로벤치마크, PlayMode: 실제 씬의 작은 한 판)
$UNITY -batchmode -projectPath . -runTests -testPlatform EditMode -testResults editmode.xml -logFile editmode.log
$UNITY -batchmode -projectPath . -runTests -testPlatform PlayMode -testResults playmode.xml -logFile playmode.log

# 실제 한 판 A/B, 배치 실행 (후보 수·CPU 시간·판정 일치. 프레임 시간·FPS·Draw Call은 기록하지 않음)
$UNITY -batchmode -projectPath . -executeMethod RebootEnemyAbBenchmark.RunRoundBatch -rebootOut Docs/Perf/EnemyAb/results/<이름> -rebootLabel <이름> -logFile round.log

# 마이크로벤치마크 (저장된 궤적 재생)
$UNITY -batchmode -projectPath . -executeMethod RebootEnemyAbBenchmark.RunMicroBatch -rebootOut Docs/Perf/EnemyAb/results/<이름> -rebootLabel <이름> -rebootTrace Docs/Perf/EnemyAb/trace/round100.trace.txt -rebootRepeats 21 -logFile micro.log
```

5절의 Editor 배치 결과는 위의 세 번째·네 번째 명령으로 만들었다. 이 Mac에서 같은 명령을 다시 돌리면 후보 수와 검증 판 수치가 그대로 다시 나왔다(CPU 시간은 실행마다 조금씩 다르다).

### 적 수를 늘린 실험 (100·200·300명)

`-rebootEnemies`에 적 수를 쉼표로 이어 적으면 차례로 돌린다. 결과는 `enemies-<수>` 폴더로 나뉘고, 모든 요약 행이 `scaling_summary.csv` 한 파일로 묶인다.

```bash
# 실제 한 판 A/B를 100·200·300명으로 차례로 (Editor 배치)
$UNITY -batchmode -projectPath . -executeMethod RebootEnemyAbBenchmark.RunRoundBatch -rebootEnemies 100,200,300 -rebootOut Docs/Perf/EnemyAb/results/<이름> -rebootLabel <이름> -logFile sweep.log

# 적 수별 마이크로벤치마크 (저장된 궤적: round100, round200, round300)
$UNITY -batchmode -projectPath . -executeMethod RebootEnemyAbBenchmark.RunMicroBatch -rebootOut Docs/Perf/EnemyAb/results/<이름>/enemies-300 -rebootLabel <이름> -rebootTrace Docs/Perf/EnemyAb/trace/round300.trace.txt -rebootRepeats 21 -logFile micro300.log
```

- 플레이어 빌드에서는 실행 인자에 `-rebootEnemies 100,200,300`을 더한다. Editor에서는 메뉴 `Tools/REBOOT Perf/Enemy A-B: Run 100-200-300 Sweep In Play Mode`를 쓴다(결과는 `results/local-sweep/`).
- 100명을 넘는 수는 성능 실험용 상한으로만 채운다. 허용하는 최대는 300명이고 그보다 큰 값은 300명으로 낮춘다. `EnemySettings` 에셋과 일반 플레이의 상한(100명)은 바뀌지 않는다. 실험용 상한을 썼는지는 `round_environment.csv`의 `experiment_enemy_cap`과 `scaling_summary.csv`의 앞쪽 세 열에 남는다.
- 세 가지를 다 돌리면 게임 시간으로 13분 30초 분량이다(수직 동기를 껐으므로 실제 시간은 기기가 낼 수 있는 속도만큼 짧다. 이 Mac에서는 Editor 배치 100초, 플레이어 창 실행 133초). 판 수를 줄이려면 `-rebootRepeats 1`을 쓴다.
- 적이 다 차기를 기다리는 시간과 측정 구간이 한 라운드(100초) 안에 들어가지 않으면 시작하기 전에 오류로 알린다.

### 시연 PC에서 프레임 시간·FPS·Draw Call까지 재기

화면에 그리는 실행이어야 한다. 둘 중 하나를 쓴다.

- **플레이어 빌드(권장)**: 빌드한 실행 파일을 인자와 함께 실행한다. 끝나면 스스로 종료한다.
  ```text
  Windows  <빌드한 실행 파일>.exe -rebootEnemyAb -rebootOut C:\reboot-perf\demo-pc -rebootLabel demo-pc-player
  macOS    open -n -W <빌드한 앱>.app --args -rebootEnemyAb -rebootOut <폴더> -rebootLabel <이름>
  ```
  - `-rebootOut`을 생략하면 `persistentDataPath/EnemyAb`에 쓴다. `-batchmode`를 붙이면 화면에 그리지 않으므로 붙이지 않는다.
  - 화면 크기와 품질 단계는 그 빌드의 설정을 그대로 쓴다. 어떤 크기로 쟀는지는 `round_environment.csv`의 `screen`에 남는다. 발표에 쓸 값은 시연할 때와 같은 화면 설정으로 잰다.
  - macOS 줄은 이 Mac에서 확인했다. **Windows에서는 돌려 보지 못했다.**
- **Editor Play Mode**: 메뉴 `Tools/REBOOT Perf/Enemy A-B: Run Round In Play Mode`. Game 창에 그려지는 동안 측정하고, 끝나면 Play Mode를 끝낸다. 결과는 `Docs/Perf/EnemyAb/results/local/`. Editor 부하가 섞인 값이다. Mac에서는 명령으로 Editor를 띄워 같은 흐름을 돌렸다(5.7절). 메뉴를 직접 눌러 시작하는 것은 확인하지 못했다. 시작한 뒤에는 끝날 때까지 다른 창을 누르지 않는다(Game 창에 포커스가 없던 판은 프레임 지표가 빈칸이 된다).

측정하는 동안(게임 시간으로 약 3분, 이 Mac의 창 실행에서는 실제로 20초 안팎) 키보드와 마우스를 건드리지 않고 창을 앞에 둔다. 창이 포커스를 잃어도 측정은 끝까지 가지만 그 판의 프레임 지표는 빈칸이 된다. 프레임 시간은 실행마다 차이가 있으므로 세 번 이상 재서 범위를 본다.

플레이어를 명령으로 빌드하면(`-buildWindows64Player <경로>`, `-buildOSXUniversalPlayer <경로>`) Unity가 `ProjectSettings`와 `Assets/Settings`의 설정 파일 몇 개를 빌드 대상에 맞춰 다시 쓴다. 이번 확인에서는 빌드할 때마다 되돌렸고 빌드 결과물은 지웠다.

조절 인자: `-rebootEnemies <수>`(기본 100), `-rebootWindowFrames <수>`(기본 900. 바꾸면 궤적 길이와 공격 시점도 같은 비율로 바뀐다), `-rebootRepeats <수>`(방식마다 시간 판 수, 기본 2).

## 8. 측정하며 확인한 것 (게임 코드는 고치지 않음)

- **격자와 Transform의 어긋남**: 적은 `RunAI`에서 Transform을 직접 옮기고 곧바로 격자에 기록된다. 그런데 적 프리팹의 Rigidbody는 kinematic + Interpolate라, 그 뒤에 Transform이 다시 쓰이는 프레임이 있다(실제 판의 위치 해시가 연속 프레임에서 같은 값으로 되풀이된다). 이때 격자에 기록된 칸과 실제 Transform이 한 걸음(0.058m) 어긋나고, 칸 경계에 걸리면 격자가 반경 안의 이웃을 놓칠 수 있다. 네 실행 모두 질의 55,414건 중 같은 1건이었다. 분리 방향 계산에만 영향을 주고, 특수 공격 적중 판정에서는 생기지 않았다.
  - 이 문제는 `Docs/UiTheme/README.md` 마지막 절과 `Docs/LevelDesign/REBOOT_HUB_LEVEL_DESIGN.md` 6절에 적어 둔 "적 이동 보간" 문제와 같은 원인으로 보인다. 원인 확정과 수정은 적 담당의 판단이 필요하다(후보: kinematic 이동에 보간을 끄거나 `Rigidbody.MovePosition`을 쓴다).
- **판마다 위치가 조금씩 다름**: 위 문제 때문에 적의 실제 이동이 물리 스텝과 프레임의 어긋남에 따라 달라진다. 같은 방식으로 두 번 돌려도 위치가 밀리미터 단위로 다르고, 적의 공격이 닿는 프레임이 한 프레임 갈리는 경우가 있다. 판정 합계(적중·처치·피격·점수)는 모든 판에서 같았다.
- **특수 공격의 비용**: 첫 특수 공격(67명 적중)의 범위 판정에 Editor에서 9.0~9.8ms, 플레이어에서 3.9~4.3ms가 들었다. 뒤의 두 번(16명, 12명 적중)은 0.13~0.40ms였다. 두 방식에서 비슷했으므로 후보 수집이 아니라 적중 처리(넉백, 상태 변경, 이벤트) 쪽 비용이다.
  - 적 수 실험에서 더 분명해졌다. 첫 특수 공격은 Editor에서 200명 17.7~18.3ms(137~139명 적중), 300명 18.7~19.0ms(182~185명 적중)였고, 플레이어에서 200명 8.0~11.2ms, 300명 8.1~10.4ms였다. 적중 한 건당 Editor 0.10~0.13ms, 플레이어 0.04~0.08ms다.
  - 같은 판의 두 번째 특수 공격은 적중 한 건당 0.015ms 안팎이었다(300명에서 92~97명 적중에 1.2~1.7ms). 처음 한 번만 비싸다는 뜻이다. 적중 효과(`CombatVfxRuntime`)가 풀이 비어 있을 때 그 자리에서 새로 만들어지는 것이 원인으로 보이지만 프로파일러로 확인하지는 않았다.
- **격자가 놓치는 이웃은 적이 많을수록 늘어난다**: 분리 이웃에서 놓친 적이 Editor 배치에서 100명 1건, 200명 4건, 300명 8건이었다(5.8절). 비율로는 반경 안의 적 수십만 명 중 한 자릿수다. 특수 공격 판정에서는 한 건도 없었다.
- **프레임 시간에 드러나는 정도(이 Mac)**: 적 100명에서 공간 분할은 AI 갱신 시간을 3분의 1 수준으로 줄인다. 그 차이(플레이어에서 약 0.38ms)는 플레이어 창 실행의 프레임 시간에는 나타나지 않았고(5.6절), Editor Play Mode에서는 유효한 한 판 기준으로 0.5~0.6ms 차이로 나타났다(5.7절). 적을 200명, 300명으로 늘리면 플레이어 창 실행에서도 0.9ms, 3.3ms 차이로 나타났다(5.9절). 어느 쪽도 시연 PC의 결과를 대신하지 못한다.
